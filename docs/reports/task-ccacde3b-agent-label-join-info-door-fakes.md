## Where the sponsor field comes from

The door contract at `f57ed82e1` had no `agentSponsor` on a community, because door.json was
generated at runtime `7f436b82` (`deploy/dev-communities`), which does not send it. The
member sponsor view is on runtime branch
`origin/coord/member-community-response-carrie-bfd5a63c` (head `eabfbcdd`, door.js change
`348cd54d`). It is **not on `deploy/dev-communities` yet**. That runtime's `sponsorView` adds
`agentSponsor: {did, handle}` to member community responses (list, `GET /:id`, join) when the
agent flag is on and the slot is valid. `handle` is the sponsor's current member id in this
community, or `null`. It is never the DID.

What changed:

- `scripts/communities/generateDoorFixtures.mjs` now points at `eabfbcdd`. After the existing
  calls, it seeds a sponsor membership (`carol-sponsor`, DID = the config's `agentSponsor`) and
  captures `communityWithSponsorMember`. door.json was regenerated by running the generator
  against a `git archive` of `eabfbcdd`. Nothing in it is hand-written.
  - `community.community.agentSponsor` is `{did: 'did:plc:gardensponsorfixture', handle: null}`,
    because the sponsor holds no membership at that point.
  - `communityWithSponsorMember.community.agentSponsor.handle` is `'carol-sponsor'`.
- `doorContract.ts` adds `DoorAgentSponsor = {did: string; handle: string | null}` and
  `DoorCommunity.agentSponsor?`. The field is optional because it is absent for non-member
  routes, with the flag off, and on runtimes before bfd5a63c. The Dev capture of 2026-10-30 has
  none.
- The contract test adds `agentSponsor` to `COMMUNITY_KEYS`. A new case checks the
  `{did, handle}` shape (handle `null`, or a member id), and that the Dev capture has none.
  `agentSponsor` on an **item** is still rejected, at both type and run level.
- New fixture helpers: `DOOR_SPONSOR_DID`, `doorCommunityWithSponsorMember()` and
  `asClientCommunity()` (the door community as `communitiesClient` hands it over, with
  `viewer_is_admin` read into `viewerIsAdmin`). `clientCommunity()` now also strips
  `agentSponsor`, since it stands for the flags-off response.

## Item by item

1. **HIGH, label rule** (`src/features/communityAgent/labelRule.ts`). An author is the agent
   only when all three hold:
   - `author.is_agent === true`;
   - `author.did` equals `community.agent.did`;
   - `community.agentSponsor.did` is non-empty.

   The label carries `sponsorHandle` from `agentSponsor.handle`, or `''` when that is null.
   `CommunityAgentConfig` is now just `Pick<Community, 'id' | 'name' | 'viewerIsAdmin' |
   'agent' | 'agentSponsor'>`, so every field it reads is a field the door sends.
   - The invented `agentDid`, `agentSponsor` (string) and `agentSponsorName` are gone.
   - `agentDisclosureUrl` (also not sent) is now an optional prop on `CommunityThreadPost`.
     It has no production caller, so no disclosure link shows until something supplies one.

     never the DID or the community name.

     `agent` and `agentSponsor`.

## Open items (found, not fixed)

1. **The runtime sponsor view is not deployed.** The Dev runtime (`deploy/dev-communities` at
   `7f436b82`) sends no `agentSponsor`. Until bfd5a63c lands there, the app shows **no** agent
   label or agent card against Dev. This is fail-closed, and the Dev-capture test pins it. Once
   bfd5a63c is on the deploy branch, regenerate door.json from that ref.
2. **Community-level drift outside the agent fields remains** in `descriptor.ts`. It still
   reads off the raw response: `role`, `config.tier`, `config.theme`, `config.brand`,
   `config.moderation`, `memberCount`, `rules`, `rulesUrl`, `runBy`, `groupUri`,
   `consentVersion`, `avatar` and `banner`. The door sends none of these. With the real door:
   - the tier is always `members`;
   - there is no member count, rules or "Run by" line;
   - `isMember` comes only from `viewer_is_admin` being present, so with the admin role off a
     real member reads as a non-member.
3. **The non-member community home cannot be reached against the door.** The door answers
   `GET /:id` with `not_found` to a non-member, so the screen shows its error state, not the
   join button. The CommunityScreen non-member tests use the flags-off member shape instead,
   which is the only door shape the descriptor reads as a non-member. This screen should
   probably route non-members to join-info.
4. **The join screen knows only the id before joining.**
   - join-info is the same for every id and names no community, agent or rules, so the
     consent copy ("I agree to the community rules") points at rules the person cannot see.
   - join-info's `wording_version` is the platform version, but the door requires
     `consentVersion >= max(platform, community wording_version)`. A community whose own
     version is higher than the platform's refuses the join (404 plus the join-info hint), and
     the screen shows "Couldn't join right now".
   - door.json's generator config has no platform `wording_version`, so its join-info is
     `null`. The happy path uses the Dev capture (`1`).
5. **The posts list label (`PostsSection`, `membersPost`) does not require a sponsor.** It
   uses the shared DID rule only (`isCommunityAgentAuthor`). The thread view (`labelRule`) also
   requires `agentSponsor`. Whether the posts list should require it as well is a product call
   under N1; it was not in this task's list.
6. `CommunityThreadPost`'s disclosure link now needs an explicit `agentDisclosureUrl` prop. The
   door sends no disclosure URL.
