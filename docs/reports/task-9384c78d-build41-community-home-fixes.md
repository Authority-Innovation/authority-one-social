## 1. "AI agent · run by {sponsorName}"

Root cause: not a missing value. The value was always passed. `babel.config.js` keeps the
source message in Release (`stripMessageField: false`), but `@lingui/core` registers its
runtime message compiler only when `NODE_ENV !== 'production'`. A message not yet in the
compiled catalog (new strings arrive with the nightly extract; `en/messages.po` has no
"run by" entry) falls back to its raw source string, and with no compiler Lingui returns
that string as is, placeholders included. Dev builds and jest compile it, which is why no
test caught it.

Every place with the literal (grep "run by" and the placeholders):
- `src/screens/Community/components/AgentCard.tsx` - "AI agent · run by {sponsorName}"
- `src/features/communityAgent/CommunityThreadPost.tsx` - "AI agent · run by @{sponsorHandle}"
  (and "@{sponsorHandle} added this agent ...", same mechanism)

Fix:
- `src/locale/messageCompiler.ts` registers `compileMessage` in every environment; it is
  imported by `src/locale/i18n.ts` and `src/locale/i18n.web.ts`. This fixes both sites and
  every other interpolated string waiting on the nightly extract (e.g. the header's
  "Run by {runBy}"). Release now renders fallbacks as dev builds already do.
  `@lingui/message-utils` is a dependency of `@lingui/core` (same 5.9.5, hoisted); it is
  imported transitively and whitelisted in `eslint.config.mjs`, like `@atproto/common-web`.
  It was not added to package.json because the lockfile could not be updated offline.
- `AgentCard` sponsor name: the sponsor's display name from the profile cache for
  `agentSponsor.did`, falling back to `agentSponsor.handle`; neither gives "AI agent".
  The door sends no display name, only `{did, handle}`.

Test: `src/screens/Community/components/__tests__/AgentCard.test.tsx`. It removes the
Lingui compiler (the Release state), loads `#/locale/messageCompiler`, and renders the card
on the door fixtures. It asserts no `{` in the rendered text for a display-name sponsor, a
handle-only sponsor, a `handle: null` sponsor, and the Dev capture, plus the thread post
sponsor line. Against the base code (base AgentCard, no compiler registration) 3 of 5 fail
with exactly the device text:
`Received: AI agent · run by {sponsorName}` and `AI agent · run by @{sponsorHandle}`.

## 2. Launch hidden while an agent is active

No admin "Manage agent" action exists in the codebase (grep "Manage agent": none), so
Launch is just hidden. `AgentLaunchControl` renders nothing when `community.agentDid` is
set, which is the same condition that shows the agent card (door `agent: {did,
is_agent: true}`). After a successful launch, the refetch brings the agent in and the
control goes away.

Tests: `launchControl.test.tsx` "an admin sees nothing while the community has an active
agent"; `CommunityScreen.test.tsx` "an admin sees no Launch while an agent is active" and
"an admin sees Launch when the community has no agent"; the One Dev 39 launch flow now
also checks that Launch is gone once the card appears.

## 3. Admin badge: which field

The Dev door at cca6020d sends **no `role` field** on the member response (door.js
`publicConfig` lines 213-230; `role` lives only on the stored membership record). No role
field was invented. The badge uses **`viewer_is_admin`** (read into `viewerIsAdmin` by
communitiesClient). `CommunityHeader` keeps "✓ Member" and adds an "Admin" badge
(`testID="communityAdminBadge"`) when `isMember && viewerIsAdmin`.

Tests (`CommunityScreen.test.tsx` "Community home - Admin badge (build 41)"): the Dev
capture (`viewer_is_admin: true`) shows the Admin badge and Member; the door member
fixture (`viewer_is_admin: false`) shows Member and no Admin badge; no `viewer_is_admin`
key shows no Admin badge.
