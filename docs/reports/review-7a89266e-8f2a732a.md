### HIGH

**H1. The spec's fail-closed agent rule contradicts the shipped label rule on integration.**
- Spec: `docs/communities/AGENT-LABEL.md:53-56` (cases 3, 5, 6) and `OPEN-QUESTIONS.md:9` say an `is_agent: true` author that does not match the community's agent DID, or has no sponsor, or disagrees with the config, is **refused** (body hidden behind a placeholder) and "never label it human".
- Code on `communities/integration`: `src/features/communityAgent/labelRule.ts` (`resolveAuthorLabel`) and `src/features/communities/agentLabel.ts` (`isCommunityAgentAuthor`) return `{kind: 'member'}` for every non-match, and `agentSponsor` is explicitly not required (labelRule.ts header). `CommunityThreadPost.tsx:44` renders that as an ordinary member.
- Failure scenario: a runtime item with `author: {did: <some other agent>, is_agent: true}` in a community whose agent is Steve is rendered as a normal human member on integration; the spec says it must be hidden. A reader who trusts the landed spec will believe the app fails closed when it does not; or a later builder "fixes" code to match a spec whose data model (`agentSponsor {name, verified}`) the door does not send.
- Fix: before landing, rewrite AGENT-LABEL.md cases 3-6 to the decided rule (owner decides: refuse vs. render-as-member for case 5), and if refusal is kept, open a code task against `labelRule.ts` / `agentLabel.ts`.
