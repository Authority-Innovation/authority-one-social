## What changed

### 1. The drift, fixed in each reader

The door's timeline page is `{items, cursor}`. An item is `{id, parentId, authorId, text,
createdAt}`, plus `is_agent`, `author: {did, is_agent}`, `sources` and `no_source` while the
runtime's agent flag is on. Items carry no `role`, no `agentSponsor`, no `body`, and no
`displayName`/`avatar`.

- `src/features/communities/membersPost.ts`: maps a `DoorItem`. Reads `text` (was `body`), uses
  `authorId` as the display name (was `author.displayName`/`avatar`, which the door never sends),
  and keeps the agent rule on `author.{did,is_agent}`.
- `src/features/communityAgent/types.ts`: `CommunityThreadPostData = DoorItem`,
  `CommunityThreadAuthor = Partial<DoorItemAuthor>`, `CommunitySource = DoorItemSource`.
  `CommunityAgentConfig` no longer has `role`; it uses `viewerIsAdmin`.
  `CommunityThreadPost.tsx` follows: it renders `text` and `authorId`, takes source links from
  `ref` and dates from `at` (the door has no `url`/`timestamp`/`position`), and the operator
  warning is for `viewerIsAdmin` (via `isCommunityAdmin`), not an owner/moderator `role`.
- `src/lib/api/feed/communities.ts`: reads `res.data.items` (was `res.data.posts`, which never
  exists) and filters with `isDoorItem`. A `null` cursor becomes `undefined`.
- `src/view/com/composer/state/submit.ts`: the community result is `posts: DoorItem[]` (it
  imported a `CommunityPost` type that did not exist).
- `src/lib/agent-runtime/communitiesClient.ts`: its response types are now aliases of the
  contract (`CommunityItem = DoorItem` and so on). Only `Community` differs, because the client
  reads `viewer_is_admin` into `viewerIsAdmin`.

Before this change, `CommunityPost`, `CommunityPostAuthor` and `CommunityMembership` were
imported from the client but did not exist in it, so the communities code did not typecheck.
The baseline `tsgo` run on `d98a57893` showed about 55 errors outside `src/locale`.

### 2. One shared door-contract type, and a contract test

- **Module:** `src/lib/communities/doorContract.ts`. It declares `DoorItem`, `DoorItemAuthor`,
  `DoorItemSource`, `DoorTimelinePage`, `DoorCommunity`, `DoorCommunityAgent`,
  `DoorCommunityList`, `DoorCommunityResponse`, `DoorJoinInfo`, `DoorItemResponse`, `DoorExport`,
  `DoorRoster`/`DoorRosterEntry` and `DoorAgentGrant`. It also has `DOOR_ITEM_KEYS` and the
  runtime guard `isDoorItem`. All four files in (1), plus the client and the composer, import it.
- **Fixtures:** `src/lib/communities/__fixtures__/door/`
  - `door.json`. The runtime has no JSON door fixtures; its door tests build responses in
    memory. So this file was **generated by running the runtime's own `door.js`**, using the
    in-memory store harness from its door test (`test/communities-agent-slot-fb477fb1.test.js`,
    `fakeWorld`/`setup`). All flags were on: communities, communityAgent, agentGrant and admins.
    It covers list (as admin and as member), community, join-info, post, reply, a timeline with
    a member post, a member reply, an agent reply with sources and a legacy item with
    `author.did: null`, plus export, roster and grant. Every body is what `handleCommunities`
    returned. The agent and legacy items were seeded into the store the way the runtime's agent
    executor and pre-R3 writes store them.
  - **Source commit:** authority-one-runtime `7f436b820e5e1b4d4bfc89a8dabb3e27e79bbaf0`
    (`origin/deploy/dev-communities`, the line Dev runs). It is recorded in `door.json` `$source`.
  - Generator: `scripts/communities/generateDoorFixtures.mjs <runtimeRoot>`. Item ids are made
    deterministic, so it gives the same output on every run.
  - `dev-runtime-2026-10-30.json`: the real Dev capture from `d98a57893`, moved here from
    `src/screens/Community/__tests__/fixtures/` so there is one fixtures folder.
  - `index.ts`: typed accessors (`doorItem('post'|'reply'|'agent'|'legacy')`, `doorTimeline`,
    `doorPage`, `doorCommunity`, `clientCommunity`, `DOOR`, `DEV_RUNTIME`). Both JSON files are
    checked against the contract with `satisfies`, so a fixture that stops matching fails tsc.
- **Contract test:** `src/lib/communities/__tests__/doorContract.test.ts`
  - Jest checks:
    - every item from every route, in both fixtures, has only contract keys and all required
      keys;
    - pages are `{items, cursor}`, never `{posts}`;
    - communities carry only `publicConfig` keys;
    - `role` or `agentSponsor` on an item is flagged;
    - the old invented `{posts:[{body, author.displayName}]}` shape is flagged.
  - Type-level checks (tsc): `@ts-expect-error` asserts that a `DoorItem` with `role`, a
    `DoorItem` with `agentSponsor`, and a `{posts}` page are all rejected. If the contract ever
    accepted one of them, the unused directive would fail tsc.

## Open items (found, not fixed: outside this task's scope)

1. **Community-level drift remains.** `descriptor.ts` and the join screen still read fields the
   door does not send: `role`, `config.*` (`tier`, `theme`, `agent`, `agentSponsor`, `brand`),
   `memberCount`, `rules`, `agentName`, `consentVersion` and `agentDid`. They are now read off
   the raw response, so the `Community` type no longer declares them and this stays a type-only
   change. The CommunityScreen test's `communityResponse` fake still uses that shape, with a
   cast. Consequences:
   - The agent sponsor (and so the agent label) never reaches the app from the door at
     `7f436b82`.
   - Runtime branch `coord/member-community-response-carrie-bfd5a63c` adds
     `agentSponsor: {did, handle}` to the member community response. It is not on
     `deploy/dev-communities` yet. Once it is, regenerate `door.json` and add the field to
     `DoorCommunity`.
2. **The join screen probably cannot work against the real door.**
   - `JoinConsent.tsx` calls `getCommunity`, which the door answers `not_found` for
     non-members. It should use `getJoinInfo`.
   - It gates on `consentVersion`, but the door sends `wording_version`.
   - Fixed here because tsc forced it: `agreeAndJoin` passed the version as a string, which
     `communitiesClient.join` refuses as `invalid_argument`. It now passes a number, and the
     JoinConsent test expects `('btb', 1)`.
3. **Composer threads longer than two posts.** `submitToCommunity` posts a thread as a chain
   (each post replies to the one before). The door's reply route refuses a parent that is
   itself a reply (`parent.parentId` gives `not_found`), so the third post of a thread fails.
